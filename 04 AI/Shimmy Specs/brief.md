# Shimmy Specs — AI Brief

**Updated:** 2026-10-28
**Status:** MVP built (framework) in a Haiku session from `mvp tasks.md`. Checks pass locally: data validation, 20 engine tests, browser smoke run (incl. reload and file://). Not yet: publish on GitHub Pages, iPad check, `/summarize-code` (P1), Supabase SQL applied (written only).

## Goal

A web app that guides the process of writing CSI specifications (architectural sections, Divisions 01–14) for Jimmy, an architect doing mostly repair work who is studying for the CCS. Project facts (an imported, free-flowing project file, a text dump, the survey) set drivers; drivers recommend sections with reasons; each section is worked through questions with bracket options; every decision is recorded by user with reasons; impacts raise flags in the section and on a project board; outputs are the PPD, outline spec and full three-part section.

## Decisions (round 1)

- MVP = the **framework** (any template runs end to end), fully static, no AI. AI ideas tracked in `todo.md` → *AI later*.
- Desktop first, professional look; color only for wayfinding (Parts, flags, division groups).
- Options are **bracket choices** inside paragraphs (`[[qid]]`).
- Flags: auto / review / decision. Hand edits are never overwritten; changes behind them raise a review flag.
- Contracts: assume AIA, pick the variant in the survey.
- Supabase: **Architecture** project (`<project-ref>`), registers tables in `public.table_index (table_name, project, purpose)`; existing tables belong to "Architecture practice" and "Quick Detail (wall sketch)". Shimmy Specs uses an `ss_` prefix; SQL written in phase 2, applied only with Jimmy's OK.
- Never store office project data; only lessons. Sketch and own projects allowed (`kind`).
- Knowledge becomes non-overlapping chapters (map in `mvp schematic.md` §10); 5xx = template specs written together.
- First templates, in order: roofing, firestopping, joint sealants, exterior painting, CMU wall, ladder fall protection, doors and hardware.

## Accounts and cloud (round 2)

- Username + password accounts in our own tables (`ss_users`, `ss_sessions`), passwords as bcrypt, sessions as hashed random tokens (30 days). Browser code only calls the `ss_` functions; tables have RLS with no policies. Password can be blank for now (decision pending, convo v0.3 Q2).
- `js/cloud.js` autosaves to the account 2 s after a change; the header light shows the state. Device-only until `index.html config block` is filled in.
- SQL `002_shimmy_specs_accounts.sql` supersedes 001. Not applied: Jimmy runs it.

## Architecture (as built)

- Plain HTML/CSS/JS in `03 Projects/Shimmy Specs/`. Engine in `js/` with no DOM (runs in Node for tests), screens in `js/screens.js`, shell in `js/app.js`.
- Data in `data/` (drivers, survey, keywords, rules, uniformat, section library, demo template) and `samples/`. `js/data.bundle.js` is generated by `tools/bundle_data.js` so the app also runs from `file://`.
- State in localStorage, export/import as `shimmy-state/1` JSON. The current project id is kept so a reload reopens it.
- Deviations from `mvp schematic.md`: paragraph edits use a textarea, not contenteditable; screens live in one file instead of one per screen.
